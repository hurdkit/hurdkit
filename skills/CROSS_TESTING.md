# Skill: Test a Cross-Compiled Driver Inside the Hurd VM

## Trigger

Use this skill when you have cross-compiled a Hurd driver (a translator,
server, or any user-space program) for `x86_64-gnu` on the Linux host and
want to prove it runs correctly inside the Debian GNU/Turd guest:

- a new binary appears after `make -C toolchain <target>`,
- you changed driver source and want to re-verify under the real Hurd kernel,
- you added a new driver to the cross-gnu pipeline and need verification steps,
- you suspect a cross-compiled binary does not behave like its source says it should.

This skill covers the *runtime* side: boot the VM, copy the driver in, run
it, and exercise it end-to-end. It does **not** cover building the cross
toolchain — see `toolchain/Makefile` and `toolchain/README.md` for that.

## Inputs

- `skills/BOOT.md` — how to build and boot the Hurd image (`make base`,
  `make provision`, `make run`/`make run-nokvm`), the SSH key layout
  (`img/keys/`), and the provisioning marker (`/root/.provisioned`).
- `toolchain/Makefile` — `make -C toolchain <target>` (verified targets:
  `binutils`, `gcc1`, `gnumach`, `mig`, `glibc`, `gcc2`, `hurd`, `9pfs`),
  `make -C toolchain verify-vm` (automates ELF check + copy + smoke test for
  9pfs), and the stage recipes that produce the driver binary. The pinned
  3p source SHAs live in `toolchain/pins.mk`; they are checked out by
  `make -C toolchain 3p-pin` before every build.
- `toolchain/README.md` — toolchain build overview and backend notes.
- `img/hurd.base.qcow2` — the provisioned, bootable Hurd base image.
- `img/keys/root_ed25519` — the root SSH key (generated by provisioning).
- The cross-built driver binary, e.g. `3p/<driver>/<binary>`.
- Optional: a test harness or server for end-to-end exercise (for a
  filesystem translator, a 9P server such as `toolchain/9p-server.py`).

## Goal

A cross-compiled Hurd driver binary is verified to:

1. be a real `x86_64` ELF "for GNU/Turd" (`file` / `readelf`),
2. execute inside the Hurd guest without crashing on startup,
3. perform its real work end-to-end (for a filesystem translator: mount a
   host directory into the guest and exercise it; for other drivers: run
   their documented invocation and check the exit status and output).

The VM base image is never modified destructively: all tests boot from a
throw-away overlay, and the driver binary is copied into the guest's
`/tmp/`.

## Procedure

### Step 1 — Build the driver with the cross toolchain

Replace `<target>` with a real `toolchain/Makefile` target. Verified targets:
`binutils`, `gcc1`, `gnumach`, `mig`, `glibc`, `gcc2`, `hurd`, `9pfs`.
For a filesystem translator, `9pfs` is the example; there is no generic
`<target>` — use the actual target name:

```sh
make -C toolchain 3p-pin        # pins 3p/ repos to verified SHAs (from toolchain/pins.mk)
make -C toolchain 9pfs          # example: builds 3p/9pfs/9pfs with x86_64-gnu-gcc
```

The driver must be built against the Hurd libraries installed in
`$HOME/opt/x86_64-gnu`. The `toolchain/Makefile` target for the driver
already passes the needed `LIBS`, `MIG`, and other variables; do not
hand-edit `3p/<driver>` — any changes needed belong in `toolchain/Makefile`.

Gate: `file 3p/<driver>/<binary>` reports `ELF ... for GNU/Turd`.

For 9pfs specifically, `make -C toolchain verify-vm` automates Steps 3–4
(ELF check, copy into the VM, `--version` / `--help` smoke test) — it builds
`9pfs` first, then copies and runs it. It assumes the VM is already booted
(Step 2); run it instead of the manual copy/smoke-test commands below if you
only need to verify 9pfs.

### Step 2 — Make sure the VM is ready

The base image must exist and be provisioned:

```sh
ls img/hurd.base.qcow2   # build it first if missing:
#   rm -f img/hurd.base.qcow2 && make base && make provision
```

Then boot from an overlay so the base stays pristine:

```sh
make run          # uses KVM when /dev/kvm is available; faster
# or:
make run-nokvm    # always without KVM; use this if KVM is not usable
```

In another terminal, wait until SSH answers:

```sh
ssh -i img/keys/root_ed25519 -o StrictHostKeyChecking=no \
    -o UserKnownHostsFile=/dev/null -p 2222 root@127.0.0.1 id
```

The guest prints `GNU debian 0.9 ...` and `uid=0(root)`.

### Step 3 — Copy the driver into the guest

```sh
scp -P 2222 -i img/keys/root_ed25519 3p/<driver>/<binary> \
    root@127.0.0.1:/tmp/<binary>
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    "file /tmp/<binary> && chmod 755 /tmp/<binary>"
```

The `file` output inside the guest must match what `file` reported on the
host — same ELF class, same interpreter `/lib/ld-x86-64.so.1`, same
"for GNU/Turd" note.

### Step 4 — Smoke test

Run the driver's simplest documented invocation and check exit status and
output:

```sh
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    "/tmp/<binary> --version"
```

If the driver has no `--version`, use whatever no-args invocation it
documents and check the exit status. **Do not pipe the output through
`head` or similar** — the pipe's exit status masks the binary's. The
command must exit 0 and print real usage/version output.

To capture exit status explicitly:

```sh
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    "/tmp/<binary>; echo EXIT=\$?"
```

`\$?` is escaped so the remote shell expands it, not your local shell.

### Step 5 — End-to-end exercise (driver-specific)

#### Filesystem translators (e.g. 9pfs)

Mount a host directory into the guest and exercise reads, writes, stat,
chmod, and mkdir.

Host terminal (leave running):

```sh
mkdir -p ~/work/<driver>-root
echo "hello from the share" > ~/work/<driver>-root/canary.txt
python3 toolchain/9p-server.py ~/work/<driver>-root 127.0.0.1:1564 &
```

Guest terminal:

```sh
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    "settrans -c /host /tmp/<binary> 10.0.2.2:1564"
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 'ls -la /host'
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 'cat /host/canary.txt'
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    'echo "written from the guest" > /host/write-test.txt'
cat ~/work/<driver>-root/write-test.txt   # must show "written from the guest" on the host
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    'mkdir /host/write-dir && stat -c %a /host/canary.txt'
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    'settrans -g -f /host; rm -rf /host'
```

If the server wedges, the mount reports `EIO` ("Computer bought the
farm"). Fix: restart the server, then `settrans -g -f /host` followed by a
fresh `settrans -c /host ...`.

#### Non-filesystem drivers

Run the driver's real work with its documented arguments and verify the
exit status and any output files it produces inside the guest:

```sh
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 \
    "/tmp/<binary> <driver-specific args>; echo EXIT=\$?"
```

`\$?` is escaped so the remote shell expands it, not your local shell.
`EXIT=` must be `0`. Copy any generated output back to the host with `scp`
if you need to inspect it there.

### Step 6 — Record results

Record the exact command output (host `file`, guest `file`, smoke-test
output, end-to-end exercise output) in a results file next to the driver
source (for example `toolchain/9pfs-verification.md`), in a table like:

| Step | Command | Result |
|---|---|---|
| Host ELF | `file 3p/9pfs/9pfs` | `ELF ... for GNU/Turd 0.0.0` |
| Guest ELF | `ssh ... 'file /tmp/9pfs'` | identical to host |
| Smoke test | `ssh ... '/tmp/9pfs --version'` | `9pfs 0.1.0`, exit 0 |
| Mount test | `ssh ... 'settrans -c /host ...'` | host files visible in guest |

Note any deviations from `toolchain/Makefile` (port numbers, server
changes, translator lifetime behavior).

## Verification table

| Check | Command | Expected |
|---|---|---|
| Host ELF format | `file 3p/<driver>/<binary>` | `ELF 64-bit ... for GNU/Turd 0.0.0` |
| Guest ELF format | `ssh ... 'file /tmp/<binary>'` | identical to host output |
| Driver runs | `ssh ... "/tmp/<binary> --version"` | prints version, exit 0 |
| End-to-end works | driver-specific (mount or real args) | driver performs its real work, exit 0 |
| Clean teardown | `settrans -g -f <mountpoint>` | translator stopped, mount gone |

If any check fails, stop: the cross toolchain or the driver source is
broken, not the VM. Check `toolchain/README.md` for backend-specific
notes before rebuilding.

## Constraints

- No root privileges: no loop mounts, no `guestfish`, no `virt-customize`.
- The base image is read-only backing for the overlay; never test against
  `img/hurd.base.qcow2` directly — always boot from `make run`/`run-nokvm`.
- The driver binary lives in `/tmp/` inside the guest; it does not survive
  a reboot of the overlay. To make it permanent, add it to the provisioning
  or rebuild the base image.
- Ports below 1024 on the host need root; test servers use an unprivileged
  port (1564) and QEMU user-net maps it to `10.0.2.2:1564` inside the guest.
- Translator stderr goes to the Mach console, not the SSH session. Use
  `--dump-9p` (for 9pfs) or the driver's debug flag to see RPC traffic on
  the invoking shell.

## Pitfalls

Common failures when testing cross-compiled drivers in the guest:

| Symptom | Likely cause | Fix |
|---|---|---|
| `file: command not found` in the guest | `file` isn't installed in the base image | install it (`apt-get install file`) or compare `readelf -h` output instead |
| `no such file or directory` when running `/tmp/<binary>` | the ELF interpreter `/lib/ld-x86-64.so.1` is missing from the guest | the driver was built against a glibc not present in the guest; rebuild the base image with the new Hurd libraries, or copy the needed `.so` files into the guest |
| `settrans: Not a translator` | the binary isn't a Hurd translator or lacks expected entry points | confirm the driver is built as a translator (links libfshelp/libports, etc.) and uses the right calling conventions |
| `settrans: Permission denied` | the mount point already has a translator, or the directory isn't writable | `settrans -g -f <mountpoint>` first to clear any existing translator |
| `connection refused` on SSH | the VM hasn't finished booting / sshd isn't up yet | retry the SSH login in a loop until it succeeds (the port accepts connections before sshd is ready) |
| driver crashes immediately on startup | missing shared libraries or unresolved symbols in the guest | run `ldd` (or `readelf -d`) on the binary inside the guest to check for missing dependencies |
| exit status masked by a pipe | `cmd \| head` reports `head`'s status, not the binary's | run without a pipe, or embed the check: `ssh ... "/tmp/<binary>; echo EXIT=\$?"` (`\$?` is escaped so it expands on the remote side). |
| mount works for reads but writes return EROFS | the translator was started with `-r, --readonly` | restart without the readonly flag |
| `EIO` / "Computer bought the farm" after a mount | the test server (e.g. 9P server) crashed or the connection dropped | restart the server, then `settrans -g -f <mountpoint>` and re-mount |

## Worked example: 9pfs

Replace `<driver>` with `9pfs` and `<binary>` with `9pfs` throughout the
steps above:

```sh
make -C toolchain 9pfs
scp -P 2222 -i img/keys/root_ed25519 3p/9pfs/9pfs root@127.0.0.1:/tmp/9pfs
ssh -i img/keys/root_ed25519 -p 2222 root@127.0.0.1 '/tmp/9pfs --version'
```

The mount test in Step 5 uses `toolchain/9p-server.py` serving a host
directory on `127.0.0.1:1564`, mapped to `10.0.2.2:1564` inside the guest
via QEMU user-net.
